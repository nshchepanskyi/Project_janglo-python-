# 1.2. Проєктування бази даних

## ERD

```mermaid
erDiagram
    ROOM ||--o{ RESERVATION : has
    GUEST ||--o{ RESERVATION : books
    USER ||--o{ RESERVATION : manages
    RESERVATION ||--o{ SERVICEORDER : includes
    GUEST ||--o{ SERVICEORDER : orders
    ROOM }o--o{ SERVICE : "includes (M2M)"
    USER ||--o{ ROOMFAVORITE : favorites
    ROOM ||--o{ ROOMFAVORITE : "starred by"
    RESERVATION ||--|| REVIEW : "one review per stay"
    USER ||--o{ REVIEW : writes
    ROOM ||--o{ REVIEW : receives

    ROOM {
        int id PK
        string number UK "101..301"
        string room_type "Single/Double/Suite"
        decimal price
        string status "Available/Occupied/Cleaning/Maintenance"
        string title "назва для публічної картки"
        string location "Kyiv, Ukraine"
        int capacity "Single 1, Double 2, Suite <= 8"
        decimal rating "0..5, default 4.5"
        string photo "шлях у media/rooms/"
    }
    SERVICE {
        int id PK
        string name UK "Breakfast, Spa, ..."
        decimal price "ціна з каталогу"
    }
    GUEST {
        int id PK
        string name
        string phone "+380..."
        string email
    }
    RESERVATION {
        int id PK
        int guest_id FK "CASCADE"
        int room_id FK "PROTECT"
        int user_id FK "SET NULL, NULL for legacy"
        date check_in
        date check_out "Night: check_out > check_in; Day: check_out = check_in"
        string stay_type "Night/Day (денне бронювання 07:00–23:59)"
        int guests ">= 1, <= місткості типу"
        string status "Pending/Checked-In/Checked-Out"
        datetime created_at
    }
    SERVICEORDER {
        int id PK
        int guest_id FK "CASCADE"
        int reservation_id FK "CASCADE, NULL для старих записів"
        string service_name "копія з SERVICES"
        decimal service_price "копія ціни на момент замовлення"
        int quantity ">= 1"
        decimal total "price × qty (auto)"
        datetime timestamp
        string status "Pending/In Progress/Completed/Cancelled"
        bool paid "оплата перед виселенням"
    }

        int id PK
        string username UK
        string email UK
        string password_hash
        bool is_staff "адміністратор"
    }
    ROOMFAVORITE {
        int id PK
        int user_id FK "CASCADE"
        int room_id FK "CASCADE"
        datetime created_at
        UNIQUE(user_id, room_id) "одна зірочка на пару"
    }
    REVIEW {
        int id PK
        int reservation_id FK "UNIQUE, CASCADE"
        int room_id FK "CASCADE"
        int user_id FK "CASCADE (автор)"
        int rating "1..5"
        text text "текст відгуку"
        datetime created_at
    }
```

**Зв’язки:**

- `Guest 1—N Reservation`, `Room 1—N Reservation` (номер захищено від
  видалення — `PROTECT`, гість видаляється каскадно — `CASCADE`).
- `User 1—N Reservation` — хто створив бронювання (`hotel_reservation.user`,
  `ON DELETE SET NULL`, допустимо `NULL` для записів, зроблених до
  запровадження ролей). Завдяки цьому звичайний користувач бачить у профілі
  **лише власні** бронювання, адміністратор — усі.
- `Reservation 1—N ServiceOrder` — додаткові послуги належать конкретному
  бронюванню (`reservation_id`, `CASCADE`; `NULL` — історичні записи),
  тому на сторінці бронювання рахують «сплатити перед виселенням».
  `Guest 1—N ServiceOrder` — каскадне видалення разом із гостем.
- `Room M—N Service` — «що є в цьому номері» (проміжна таблиця
  `hotel_room_services` з `UNIQUE (room_id, service_id)`); галочки ставить
  адміністратор при додаванні номера.
- `User 1—N RoomFavorite`, `Room 1—N RoomFavorite` — **обране** (Фаза 3):
  обидва FK з `CASCADE`, пара `(user_id, room_id)` **унікальна** — зірочка
  або є, або її немає (toggle). Видалення номера чи користувача прибирає
  й зірочки.
- `Reservation 1—1 Review` — **відгук** (Фаза 3): `OneToOneField` на
  бронювання (`UNIQUE`, `CASCADE`) фіксує правило «одне повідомлення на
  бронювання» на рівні БД; `room_id`/`user_id` з `CASCADE`, `rating`
  з `CHECK 1..5`. Разом із обов’язковим статусом `Checked-Out`
  (перевіряє вʼю) це дає чесну схему «гість реально жив у цьому номері»;
  середня оцінка по `room_id` перетікає в `hotel_room.rating`
  (`recalc_room_rating`, сигнали `post_save`/`post_delete`).
- `User` (штатний `auth_user` Django) зберігає роль у полях
  `is_staff`/`is_superuser` (адміністратор) та хешує паролі (PBKDF2) —
  заміна `users.json` + `auth.py` з відкритим текстом.

Мапінг Flet → Django: `storage/rooms.json → hotel_room`,
`guests.json → hotel_guest`, `reservations.json → hotel_reservation`,
`service_orders.json → hotel_serviceorder`, `users.json → auth_user`,
`SERVICES_CATALOG` (код) → **`hotel_service`** (окрема таблиця),
фото номерів → файли в `media/rooms/` (поле `photo`);
`hotel_roomfavorite` і `hotel_review` — **нові сутності без аналога у Flet**
(Фаза 3, персоналізація гостя).

## Опис створених SQL-скриптів

Скрипти лежать у `hotel/sql/` і дублюють схему міграцій
`hotel/migrations/` у вигляді чистого SQL (для звіту й ручного розгортання).

### `01_schema.sql` — створення схеми (SQLite)

- `hotel_room`: `number UNIQUE`, `CHECK` на тип/статус, `price >= 0`;
  поля публічної картки `title`, `location`, `photo` (шлях у `media/`),
  `rating` (`0..5`) та `capacity` із **`CHECK` місткості за типом**
  (`Single <= 1`, `Double <= 2`, `Suite <= 8` — аналог `capacity_error()`).
- `hotel_service`: `name UNIQUE`, `price >= 0` — каталог послуг у БД
  (порт `SERVICES_CATALOG`).
- `hotel_room_services`: M2M «номер ↔ послуга», `UNIQUE (room_id, service_id)`.
- `hotel_guest`: `name`, `phone`, `email`.
- `hotel_reservation`: FK на гостя (`ON DELETE CASCADE`), номер
  (`ON DELETE RESTRICT` — аналог `PROTECT`) і користувача
  (`ON DELETE SET NULL`), `guests >= 1`, `stay_type` (`Night`/`Day`,
  міграція `0005`), `CHECK (check_out > check_in)` **для нічлігу** або
  `check_out = check_in` **для дня**;
  індекси за `guest_id`, `room_id`, `user_id`, `status` та
  `idx_reservation_dates (check_in, check_out)` — швидкий пошук перетинів
  дат (`check_in < other.check_out AND check_out > other.check_in`) і днів,
  що потрапили в інтервал нічлігу.
- `hotel_serviceorder`: `quantity >= 1`, `service_price >= 0`, `total`
  (обчислюється в `ServiceOrder.save()` як `price × quantity`),
  FK `reservation_id` (додаткові послуги бронювання), `paid`
  (оплата перед виселенням), `CHECK` на статуси, індекси за
  `guest_id`, `reservation_id`, `status`.
- `hotel_roomfavorite` (Фаза 3): `UNIQUE (user_id, room_id)` — одна
  зірочка на пару «користувач ↔ номер», індекс за `room_id`.
- `hotel_review` (Фаза 3): `reservation_id UNIQUE` — одне повідомлення
  на бронювання на рівні БД, `CHECK (rating >= 1 AND rating <= 5)`,
  індекси за `room_id` (сторінка місця) і `user_id`.
- `PRAGMA foreign_keys = ON`.

### `02_seed.sql` — початкові дані

Порт `create_default_rooms()` + `SERVICES_CATALOG` з `hotel_data.py`:
5 номерів за замовчуванням (101/102 Single $50, 201/202 Double $80,
301 Suite $150) разом із даними публічних карток — назва, локація,
місткість, рейтинг і порожнє `photo` (колонка `NOT NULL` із міграції 0003;
без неї `OR IGNORE` мовчки кидав би рядки):

```sql
INSERT OR IGNORE INTO hotel_room
    (number, room_type, price, status, title, location, capacity, rating, photo) VALUES
    ('101', 'Single', 50, 'Available', 'Cozy Single with City View', 'Kyiv, Ukraine', 1, 4.6, ''),
    ('202', 'Double', 80, 'Available', 'Comfort Double Room',       'Kyiv, Ukraine', 2, 4.7, ''),
    ('301', 'Suite', 150, 'Available', 'GrandStay Suite',           'Lviv, Ukraine',  3, 4.9, '');
```

Далі — **каталог із 13 послуг** (`hotel_service`: Breakfast $10 …
Conference Room $100) і прив’язка «що є в цьому номері»
(`hotel_room_services`, M2M — відповідає демо-бекфілу міграції 0004).

### `03_more_rooms.sql` — демонстраційне розширення

Опціональний скрипт для об’ємнішої демо-бази: **60 додаткових номерів**
(20 Single `103–122`, 24 Double `203–226`, 16 Suite `302–317`) згенерованими
назвами/локаціями/рейтингами та **каталогом послуг** (`INSERT OR IGNORE
INTO hotel_service` — дублює `02_seed`, повторний запуск ідемпотентний).
Поле `photo` лишається
порожнім — фото вантажать формою в панелі керування або `/admin/`.
`INSERT OR IGNORE` + `number UNIQUE` роблять запуск ідемпотентним.

Каталог послуг використовує **копіювання ціни** в замовленні
(`service_price` на момент покупки) — зміна прайса в `hotel_service`
не ламає історію рахунків.

### Міграції Django

```bash
py manage.py makemigrations hotel   # → 0001_initial.py і наступні
py manage.py migrate                 # застосовує схему + auth/session/admin
```

| Міграція | Що додає |
|---|---|
| `0001_initial` | `Room`, `Guest`, `Reservation`, `ServiceOrder` (порт JSON-сховища) |
| `0002_reservation_user` | `Reservation.user` (`SET NULL`) — зв’язок «запис ↔ користувач» для ролей |
| `0003_…_room_capacity_…` | публічна картка: `Room.title/location/capacity/rating/photo` + `Reservation.guests` |
| `0004_service_…_paid_…` | таблиця `Service` (каталог), `ServiceOrder.reservation` + `paid` |
| `0005_reservation_stay_type` | `Reservation.stay_type` (`Night`/`Day`, default `Night`) — денне бронювання; додаюча міграція, наявні записи не змінює |
| `0006_review_roomfavorite` | таблиці `Review` (відгуки: `OneToOneField reservation`, `rating 1..5`) і `RoomFavorite` (обране: `UNIQUE (user, room)`) — додаюча міграція, наявні записи не змінює |

Перевірка: `py manage.py check` — без помилок; `py manage.py test hotel` — **95/95**.
