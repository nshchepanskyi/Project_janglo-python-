# 1.3. Опис програмної реалізації

Django-проєкт у корені репозиторію: `config/` (налаштування) + застосунок `hotel/`
(+ `manage.py`, `requirements.txt`). Серверний рендеринг (MVT): моделі →
в’юхи → шаблони. Публічна частина й панель керування використовують
**спільний layout** (`base_public.html`).

Розгорнута версія працює на Render із PostgreSQL у Frankfurt; Django читає
підключення з секретної змінної `DATABASE_URL`. Локальний запуск може
використовувати SQLite. Актуальні сторінки сайту та їхні знімки наведені в
[аналізі контрольного прикладу](1.4.%20Аналіз%20контрольного%20прикладу.md#актуальна-розгорнута-версія).

## Моделі (`hotel/models.py`) — порт `hotel_data.py`

| Клас Flet | Модель Django | Поля / особливості |
|---|---|---|
| `Room` | `Room` | `number` unique, `room_type` (Single/Double/Suite), `price` Decimal, `status` (Available/Occupied/Cleaning/Maintenance); **поля публічної картки**: `title`, `location`, `capacity` (місткість), `rating`, `photo` (ImageField → `media/rooms/`), `services` M2M → `Service` («що є в номері»); `clean()` забороняє від’ємну ціну **й порушення місткості за типом** (`capacity_error`), властивість `display_title` |
| `Guest` | `Guest` | `name`, `phone` (з кодом країни, напр. `+380…`), `email` |
| `Reservation` | `Reservation` | FK `guest` (CASCADE), FK `room` (PROTECT), **FK `user` (SET NULL)** — хто створив запис (для звичайного користувача = він сам); `check_in/out` DateField, **`guests`** — кількість гостей; `status`; **`stay_type`** (`Night`/`Day`) — **денне бронювання** (заїзд 07:00 → виїзд 23:59 того самого дня, `check_out = check_in`; константи `STAY_*`, `DAY_CHECK_IN_TIME/DAY_CHECK_OUT_TIME`); `clean()` — для нічлігу `check_out > check_in`, для дня — одна дата («A day stay is one day only»), **відсутність перетину дат** через Q-хелпер `conflict_q()` (день займає весь календарний день: конфліктує з нічлігом, що накриває дату, включно з межами, та з іншим днем на ту саму дату; сусідні дати нічлігу дозволені), місткість гостей проти типу номера; властивості `is_day_use`, `nights` (для дня — 0), `days` (для дня — 1), `check_in_time/check_out_time`, `amount = price × days`, `fee` (12%), `total`, `extras_total`, `extras_due` (до сплати перед виселенням) |
| `ServiceOrder` | `ServiceOrder` | **FK `reservation` (CASCADE, NULL для старих записів)**, FK `guest` (CASCADE), `service_name`/`service_price` — **копії з каталогу на момент замовлення**, `quantity`, `total` (авто в `save()`), `timestamp` (auto), `status`, **`paid`** — оплата перед виселенням |
| `SERVICES_CATALOG` (код) | `Service` | **каталог у базі даних**: `name` unique, `price`; наповнюється міграцією/`03_more_rooms.sql`, редагується в `/admin/`; M2M з `Room` |
| — | `RoomFavorite` **(нова, Фаза 3)** | **обране**: FK `user` (CASCADE, `related_name=favorite_rooms`), FK `room` (CASCADE, `related_name=favorited_by`), `created_at` (auto); **`unique_together` (user, room)** — одна зірочка на пару; toggle робить `favorite_toggle_view` |
| — | `Review` **(нова, Фаза 3)** | **відгук гостя, який реально жив у номері**: **`OneToOneField` `reservation`** (одне повідомлення на бронювання), FK `room`, FK `author` (User), `rating` 1–5 (`clean()` + `PositiveSmallIntegerField`), `text`, `created_at` (auto); порядок — новіші згори; **середня оцінка перетікає в `Room.rating`** через `recalc_room_rating()` (сигнали `post_save`/`post_delete` — видалення в `/admin/` теж перераховує зірочки; поки відгуків немає, рейтинг лишається початковим із seed) |
| `USERS`/`auth.py` | штатний `User` | хешовані паролі, `create_user` / `authenticate` |

Бізнес-функції — прямий порт з `hotel_data.py`:
`calc_reservation_revenue()`, `calc_service_revenue()`, `calc_total_revenue()`,
`get_occupancy_rate()`, `get_services_summary()`, `arrivals_count()`.

Нове (публічна частина): `search_rooms(location, check_in, check_out, guests,
stay_type)` — фільтр за локацією/місткістю та **виключення зайнятих дат**
(перетин інтервалів через `conflict_q`; для дня достатньо лише `check_in`);
`room_is_free(room, dates, stay_type)` — бейдж вільності картки;
`calc_service_fee()` — сервісний збір 12%; `ROOM_CAPACITY_LIMITS`,
`MAX_GUESTS`, `capacity_error()` — перевірки місткості.

**Ролі та обмеження доступу** (реалізація в `hotel/views.py`):

- `is_admin(user)` — `is_staff or is_superuser`; `admin_required` — декоратор
  поверх `login_required`: для звичайного користувача повертає редирект
  на `/profile/` із повідомленням «Access restricted to administrators»
  (uk: «Доступ лише для адміністраторів»).
- `@admin_required`: `dashboard_view`, `rooms_view`, `guests_view`.
  `reservations_view` і `reservation_detail_view` доступні після входу, але:
  список для звичайного користувача = `filter(user=request.user)`,
  зміна статусу (`action=status`) — лише адмін; створення прив’язує
  `Reservation.user = request.user` і підставляє email з профілю;
  сторінка бронювання відкрита його власнику або адміну.
- **Публічні сторінки без входу:** `/`, `/places/`, `/places/<номер>/`,
  `/pages/.../`, `/login/`, `/register/`, `/lang/`, `/theme/`.
- Після входу/реєстрації редирект за роллю: `home_redirect()` →
  адмін на `/dashboard/`, користувач на `/profile/`; запитана сторінка
  зберігається в `?next=`.
- Контекст-процесор `hotel/context_processors.ui_prefs` додає `is_admin`
  у всі шаблони: **шапка** (role-меню; сайдбару в проєкті нема) показує
  адміну Dashboard/Rooms/Guests, користувачу — «Мої бронювання»,
  аноніму — кнопку Sign In; повідомлення `messages` проходять через
  `{% tr %}` (EN/UK).

Ключові рішення:

- **Бронювання:** гість створюється при кожному бронюванні (як у Flet —
  `create_guest` + `create_reservation`); повний `full_clean()` перевіряє
  дати, **перетин із активними бронюваннями** та місткість; номер стає
  `Occupied`, `Checked-Out` повертає його в `Available` (якщо немає інших
  активних записів). Публічна кнопка «Book» веде на ту саму форму з префілом.
- **Номери:** видалення заборонено, якщо є хоч одне бронювання
  (`Reservation.objects.filter(room=...).exists()`) або статус ≠ `Available` —
  точний порт правила з `rooms.py`; фото зберігається в `media/rooms/`.
- **Додаткові послуги:** замовлення — на сторінці бронювання
  (мультивибір `service` + `qty_<id>`), прив’язка до `Reservation`,
  копія ціни; **виселення неможливе, поки `extras_due > 0`**
  («Pay the extras before checkout»), кнопка «Pay before checkout»
  позначає `paid`.
- **Автентифікація:** вхід за юзернеймом **або** email (порт `login_user`);
  валідація реєстрації 1-в-1 з `auth.py` (≥3 / ≥6 / email-формат / унікальність).
- **Доступи:** публічні сторінки — без входу; бронювання й профіль —
  `@login_required`; дашборд/номери/гості — `@admin_required`.
- **Обране (Фаза 3):** зірочка на картках і сторінці місця — звичайна
  POST-форма з CSRF (без JS): для залогіненого — toggle `RoomFavorite`,
  для аноніма — редирект на `/login/?next=`. Лічильник зірочок — у шапці
  (`user.favorite_rooms.count`); сторінка `/favorites/` перелічує картки
  через `_fav_annotate()` (ознака «в обраному» на картку додається одним
  SQL-запитом для всієї добірки).
- **Відгуки (Фаза 3):** чесна схема «гість реально жив у цьому номері» —
  `_create_review()` приймає POST на сторінці місця і перевіряє, що
  бронювання належить автору, має статус `Checked-Out` **з цим самим
  номером** і ще не має відгуку (`OneToOneField` — одне повідомлення на
  бронювання). Форма показується лише «готовим» гостям (`reviewable`),
  при кількох виселеннях — вибір проживання. Після збереження сигнал
  перераховує `Room.rating` — зірочки на картках стають «живими»;
  модерація — `/admin/` (перегляд, видалення з перерахунком рейтингу).
- **Дати з пошуку переносяться:** лінки карток дописують поточний
  querystring (`{% querystring %}` лише коли GET не порожній) — з каталогу
  на сторінку місця приходять `check_in/check_out/guests`; кнопка Book
  веде на `/reservations/` вже з гостями.

## Шаблони, i18n, тема

- `hotel/templates/hotel/`: **`base_public.html`** — єдина шапка
  (role-меню, EN/UK, тема, користувач, **лічильник «Обране»**) і футер
  (Terms/Privacy/Help); `base.html` успадковує її для адмін-сторінок —
  панель керування виглядає так само, як публічна частина. Далі `home`,
  `places`, `place` (відгуки + форма), `favorites`, `_place_card`
  (зірочка ★/☆), `_search_panel`, `page`, `dashboard`, `rooms`,
  `reservations`, `reservation`, `guests`, `login`, `register`, `profile`.
- **Профіль** (`profile_view`): картка акаунта з даними користувача;
  зміна email — форма з перевіркою унікальності; зміна пароля — штатна
  `PasswordChangeForm` + `update_session_auth_hash()` (сесія не «викидає»
  користувача після зміни пароля). Порівняння з Flet: `auth.update_profile` /
  `auth.change_password` (збереження в `users.json`) замінено на ORM+auth Django.
- `l10n.py` скопійовано з Flet-версії (переклади повідомлень, статусів,
  цін); мова зберігається в сесії, тег `{% tr "Ключ" %}`
  (`templatetags/tr_tags.py` + `context_processors.ui_prefs`).
- Тема — сесія `theme` + CSS-змінні у `static/hotel/style.css`
  (порт `theme.py`: `_LIGHT`/`_DARK` → `:root` / `[data-theme="dark"]`);
  публічна частина додатково має зелений бренд у `static/hotel/landing.css`.
- **Без JS у бізнес-логіці:** усі перевірки та розрахунки — на сервері
  (Python), форми працюють як звичайні GET/POST. Клієнтський JS —
  лише покращення: `app.js` (лічильник KPI, прогрес-смуги, появність
  карток, **day-режим форми бронювання** — ховає поле виїзду й підставляє
  дату заїзду, без нього поле лишається видимим), `cal.js` (власний
  календар для полів дат із форматом за мовою; без нього працюють нативні
  `input[type=date]`).
- **Анімації** (блок у `style.css`/`landing.css` + `app.js`):
  поява карток і KPI (stagger), лічильник чисел у KPI, розкриття
  прогрес-смуг дохіду, hover-підйом карток/кнопок, акцентна смужка
  активного пункту меню, виїзд повідомлень, ореол фокусу у полях,
  м’який перехід теми; усе вимикається через `prefers-reduced-motion`.
- Адмінка: `hotel/admin.py` (Room, Service, Guest, Reservation, ServiceOrder,
  **Review** — модерація відгуків, **RoomFavorite**) —
  бонус Django-версії, у Flet аналога не було; каталогом послуг тут можна
  редагувати позиції.
